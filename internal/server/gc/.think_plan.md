# 请求记录清理改造计划

## SQLite 体积保护与请求详情保留策略（2026-09-05）

### 已确认事实

- SQLite 的请求详情不在独立表中，而是存放在 `requests` 与 `request_executions` 的 JSON 字段。
- GC 每日由 `Config.CRON` 触发，已有 SQLite `VACUUM` 能在清理后回收文件空间。
- 备份的 `usage_requests` 对应 `requests` 表；`request_executions` 当前不在备份数据中。

### 目标与边界

- 仅对 SQLite 生效；数据库文件大小达到 2 GiB 时清理旧请求详情，保留按 `created_at DESC` 排序的最近 30 条请求详情。
- 清理只删除大字段，不删除请求元数据、执行元数据或用量统计；保留的 30 条请求及其执行详情完整不变。
- 备份同时跳过 `usage_logs` 与 `usage_requests`，只保留非日志业务表；旧备份中的日志仍保持兼容恢复。
- SQLite 体积检查只在 GC 入口执行，并默认设置 10 分钟冷却窗口；同一 Worker 在窗口内重复触发 GC 时不重复读取 SQLite 体积。
- 自动备份使用固定文件名 `axonhub-backup.json` 覆盖写入，并清理历史时间戳备份，只保留一份备份文件。
- 清理完成后执行已有 VACUUM，实际回收 SQLite 文件空间由 `VacuumEnabled` 控制。

### 实现路径

- 从 Ent SQL driver 获取 SQLite dialect，并从 SQLite `PRAGMA page_count` 与 `PRAGMA page_size` 计算文件逻辑大小；非 SQLite、内存数据库或无法获取大小时跳过体积清理。
- 通过 ID 游标分批选取第 31 条及更早的 `requests`，清空 `requests` 的请求头、请求体、响应体和响应分片；同步清空这些请求对应的 `request_executions` 大字段及响应头。
- 将体积检查接入每日 `runCleanup`，与用户配置的按天删除策略独立，避免阈值策略受 retention 开关影响；通过 `SQLiteRequestDetailsCheckInterval` 防止重复检查。
- 保留 `IncludeUsageStats` 与 `IncludeRequestLogs` 配置字段以兼容现有 GraphQL/配置数据，但新备份实现不再导出 `usage_logs` 或 `usage_requests`。
- 固定备份对象名并在成功写入后删除旧的 `axonhub-backup-*.json` 文件，避免按保留天数累积多份备份。

### 回归验证

- GC 测试固定 SQLite page 数阈值，验证达到阈值时只清理第 31 条以前的详情，未达到阈值时不改动详情，且执行记录与元数据保留。
- GC 测试验证检查间隔内只读取一次数据库体积。
- Backup 测试验证即使开启日志或使用统计选项也不生成 `usage_logs`、`usage_requests`，并验证旧备份日志仍可恢复。
- 自动备份测试验证固定文件名覆盖并清理历史时间戳备份。
- 运行定向 `go test` 与 `gofmt`/`git diff --check`；不运行仓库禁止的全量 build/lint。

## 根因

系统设置中的“立即清理”调用的是按保留天数执行的异步 GC。现有 `cleanupRequests` 在天数小于等于 0 时直接返回，因此该入口不能表达“删除全部请求记录”，且近期请求不会被删除。

## 方案

新增独立的 `clearAllRequestRecords` GraphQL mutation：由 GC Worker 分批删除全部请求执行记录、请求关联的用量日志和请求记录，并在删除数据库记录前清理非数据库存储中的请求/响应对象。该操作不复用保留策略，也不受保留 Trace 规则影响。

前端在存储策略卡片中保留原有按策略清理入口，增加独立的危险操作确认按钮；成功后刷新请求、执行记录和用量日志相关查询缓存。

## 验证

增加 GC Worker 回归测试，验证请求、执行和用量日志全部删除；执行定向 Go 测试、前端构建和 `git diff --check`。
